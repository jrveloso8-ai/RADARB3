===============================================================================
COMO LER ESTE RELATÓRIO
===============================================================================
Cada achado é classificado como:
  MEDIDO    = vem de fato de uma API/fonte real, sem manipulação que descaracterize.
  DERIVADO  = calculado a partir de dado real com fórmula transparente e razoável.
  ESTIMADO  = aproximação/heurística explícita, deveria ser rotulada como tal na tela.
  SIMULADO  = valor fixo, inventado ou de fallback apresentado como se fosse real/ao vivo.
  INDISPONIVEL = corretamente tratado como N/D (comportamento correto, citado como boa prática).

Severidade de risco de decisão: CRÍTICA / ALTA / MÉDIA / BAIXA — conforme o dano provável se o
usuário confiar no número para decidir uma operação real.

qualquer API — são valores digitados no código-fonte e NUNCA mudam.
Classificação: SIMULADO rotulado como MEDIDO.
Por quê é grave: a aba abre com um badge "Sincronização Ao Vivo" e o rótulo "Feeds Oficiais
TradingView em Tempo Real" logo abaixo dos mesmos números fixos, e a tela é a primeira que o

1.2 [ALTA] Termômetro de Sentimento — "Histórico das últimas 24h" é gerado por função seno, não é histórico real.
Arquivo: src/lib/domain/sentiment.ts, função `calculateMarketSentiment`, bloco `hourlyHistory` (linha ~394)
O gráfico de 24 horas do termômetro de sentimento é calculado assim:
  hOffset = Math.sin((h / 24) * Math.PI * 2) * 6
  hScore = score atual + hOffset
Ou seja, não existe persistência de scores passados — a cada carregamento de página o "histórico"
é recriado matematicamente a partir do score do momento, formando sempre a mesma onda senoidal.
Classificação: SIMULADO rotulado como histórico real ("Histórico das últimas 24 horas").
Risco: qualquer leitura de "tendência do sentimento ao longo do dia" feita pelo usuário sobre
esse gráfico é uma ilusão de padrão sem base factual nenhuma.

1.3 [ALTA] Pilares "Curva de Juros & Risco Fiscal Brasil" e "Fluxo Institucional & Estrangeiro na B3" não usam nenhum dado de juros ou de fluxo — usam só a variação do ETF EWZ.
Arquivo: src/lib/domain/sentiment.ts, linhas ~264-285
Os dois pilares (25% e 20% do peso total do termômetro, respectivamente) são derivados
inteiramente de `ewz.changePct` (variação do ETF "Brasil" negociado em NY) através de bandas

de DI Futuro, Tesouro, Boletim Focus ou fluxo estrangeiro B3 (que existe publicamente) em
nenhum lugar do código.
Classificação: SIMULADO/ESTIMADO grosseiro apresentado com nomenclatura de dado oficial
("Fluxo Institucional e Estrangeiro na B3" soa como o dado real que a B3 publica diariamente).

1.4 [MÉDIA] Pesos e limiares do score de sentimento (20%/20%/15%/25%/20%; limiares como
"SPY < -1% → score 30") são heurísticas do desenvolvedor sem lastro estatístico/backtest.
Isso por si não é "fabricação" (o pipeline usa preços reais quando disponíveis — ver 1.5), mas o

não como um índice de sentimento validado.
Classificação: DERIVADO com rótulo overclaiming.

1.5 [MÉDIA] Fallback silencioso para cotações globais quando o fetch ao Yahoo Finance falha.
Arquivo: src/lib/services/market-quotes.ts, `fetchLiveMarketQuote`
Se a chamada não-oficial à Yahoo Finance (`query1.finance.yahoo.com`, endpoint não documentado)

qualquer indicação na tela de que os dados são de fallback e não ao vivo.
Classificação: contágio SIMULADO→MEDIDO sem aviso. Usa endpoint de terceiro não oficial (risco de
quebra sem aviso).

MÓDULO 2 — RADAR DE OPORTUNIDADES (OpportunityRadarView.tsx / opportunity-radar.ts / api/opportunities)
===============================================================================
Este é o módulo com maior concentração de achados de risco CRÍTICO, pois gera recomendações de
operação (estrutura, strikes, prêmio estimado, probabilidade de lucro) que o usuário pode
executar com dinheiro real.

2.1 [CRÍTICA] "Score de Convicção" (0-100, exibido em destaque em cada card) é uma constante fixa por regra, não um cálculo.
Arquivo: src/lib/domain/opportunity-radar.ts
Cada função de detecção atribui um número fixo, escrito diretamente no código, independente do
ativo: divergência de alta = 88, divergência de baixa = 84, bull spread = 87, bear spread = 83,
iron condor = 89, the wheel = 92, intermarket brent = 86, intermarket minério = 85, agro alta
convicção = 88 / demais = 78. Não há backtest, não há regressão, não há ajuste por ativo — é o
mesmo "88" para qualquer papel que caia na mesma condição if/else.
Classificação: SIMULADO apresentado como métrica quantitativa de convicção.
Risco: o usuário decide "confiar mais" em oportunidades com convictionScore mais alto — mas o
número não mede nada específico do ativo, é apenas um rótulo do branch de código que disparou.

2.2 [CRÍTICA] "Probabilidade de Lucro" (PoP) também é constante fixa por regra, não estatística real.
Mesmo arquivo, campo `probabilityOfProfit`. Ex.: divergência de alta = 68%, divergência de baixa
= 65%, bull spread = 72%, bear spread = 68%, iron condor = 76%, the wheel = 82%, intermarket = 70-
72%. Nenhuma dessas probabilidades vem de simulação de Monte Carlo, delta da opção ou dado
histórico de acerto da estratégia — são chutes fixos embutidos no código-fonte.
Classificação: SIMULADO rotulado como probabilidade estatística.

2.3 [CRÍTICA] Prêmio/débito/crédito estimado das estruturas de opções é uma % arbitrária do preço à vista — não vem de cotação real de opção.
Ex.: `debitEst = spotPrice * 0.02` (Bull/Bear Spread), `premiumEst = spotPrice * 0.025` (The
Wheel), `creditEst = spotPrice * 0.015` (Iron Condor). Isso significa que os campos
"maxProfitEst"/"maxLossEst" mostrados ao usuário — em R$ por ação e por lote de 1.000 — são
inventados a partir de uma porcentagem fixa do preço da ação, e não das cotações reais de opções
que o próprio sistema já sabe buscar (via `brapiService.getOptionAnalytics`, usado em outros
módulos). O Radar de Oportunidades não usa essa fonte real para as opções que ele mesmo sugere.
Classificação: SIMULADO apresentado como estimativa de prêmio de mercado.

2.4 [CRÍTICA] IV ATM usada para decidir "regime de volatilidade" é uma estimativa artificial (HV × 1,05), não a IV real de mercado.
Arquivo: src/app/api/opportunities/route.ts, linha 85: `ivAtm: hv21 * 1.05`
Esse valor entra na função `classifyVolatilityRegime` (lib/domain/volatility.ts), que por sua vez
decide se "a estrutura X é favorável para venda de crédito" — inclusive para a recomendação de
Iron Condor mostrada com "RENDA RECORRENTE" e convictionScore 89. A função de classificação em si
é bem escrita, mas recebe um insumo fabricado, sem qualquer flag na tela avisando que o IV usado
não é real (é apenas 105% da volatilidade histórica).
Classificação: contágio SIMULADO → verdito aparentemente MEDIDO (ver seção sobre contágio no
método da skill: um número fabricado alimentando um cálculo correto ainda produz um resultado
não confiável).

2.5 [ALTA] Fallback de análise fundamentalista: se a chamada de fundamentos falhar/expirar, o ativo é tratado como "APROVADO, Score 75/100" por padrão — sem rodar o motor real de análise.
Arquivo: src/app/api/opportunities/route.ts, linhas 59-71
  let fundamentalStatus: 'APROVADO' | 'REPROVADO' = 'APROVADO';
  let fundamentalScore = 75;
  try { ... } catch { /* Manter defaults seguros em caso de timeout */ }
Isso é especialmente grave porque o motor real (`analyzeFundamentals`, em lib/domain/fundamentals.ts)
é rigoroso e bem construído (ver Módulo 3.2 — ele reprova por padrão quando faltam dados). O
atalho no Radar de Oportunidades ignora esse rigor: uma falha de rede (comum sob rate limit da
BRAPI sem token) vira automaticamente uma aprovação fictícia de score 75, que é score suficiente
para disparar a recomendação "The Wheel Strategy" (exige score >= 70) com convictionScore 92 e
o rótulo "Empresa sólida aprovada no CNPI-P".

2.6 [ALTA] Commodities agrícolas (Milho e Boi Gordo Futuro B3) têm PREÇO sempre fixo — apenas a variação percentual tenta ser real.
Arquivo: src/lib/services/market-quotes.ts, linhas 144-156 e src/app/api/opportunities/route.ts,
linhas 30-34.
  cornB3Est = { price: 63.80, changePct: <tentativa real via CBOT> }
  boiB3Est = { price: 244.50, changePct: <tentativa real via CME> }
  sojaPrice: 134.50  (este nem tenta — é sempre fixo, também o changePct de soja no route.ts usa
                       fallback de -0.65 se a chamada falhar)
Relevância direta: o usuário mantém projetos ativos de inteligência de mercado para milho/boi
(Milho Trader, Agro Intelligence B2B) — este módulo do Radar B3 apresenta um preço de futuro B3
que nunca é atualizado, sob o rótulo de commodity "em tempo real".
Classificação: SIMULADO (preço) + ESTIMADO/proxy (variação, que na verdade vem do contrato CBOT/
CME internacional, não do contrato B3 local — câmbio e base logística não são considerados).

2.7 [MÉDIA] `dte: 14` (dias até o vencimento) é fixo para todos os ativos, e `maxPain:
quote.regularMarketPrice` (route.ts, linha 88) faz o Max Pain — que é uma métrica real calculável
a partir do open interest — ser simplesmente igual ao preço à vista, sem nenhum cálculo. Nesse
mesmo arquivo o sistema tem uma função de Max Pain real e correta (`calculateMaxPain`, em
black-scholes.ts) que não é usada aqui.

--- 3.2 Submódulo Fundamentos (CNPI-P) ---

3.2.1 [POSITIVO — usar como referência de boa prática] O motor `analyzeFundamentals`
(lib/domain/fundamentals.ts) é o módulo mais bem construído do sistema em termos de proveniência:
todo campo ausente vira explicitamente "N/D" com 0 pontos (nunca um valor inventado); todo ajuste

Isso gera dois riscos: (a) Gregas calculadas com 14% divergem de Gregas calculadas com 10,75% para
o mesmo instrumento, dependendo de qual caminho de código foi usado; (b) conforme a Selic mudar
(é uma taxa que muda por decisão do Copom), todos os três pontos precisam ser lembrados e
atualizados manualmente — hoje nenhum é.

7.2 [BAIXA] Contador "Investidores Únicos Hoje" tem piso artificial de 1.
Arquivo: app/api/analytics/track/route.ts, linha 83: `uniqueToday: Math.max(analytics.uniqueHashes.length, 1)`
E no modal de diagnóstico (Navbar.tsx, linha 260): `{uniqueVisitors || 1} visitante único` — ou
seja, mesmo que a contagem real seja 0 (ninguém visitou, ou a leitura em disco falhou em ambiente
serverless read-only, cenário que o próprio código antecipa em comentário), a tela nunca mostra
"0" — sempre mostra pelo menos "1 investidor único hoje". O mecanismo de contagem em si (hash SHA-
256 de IP+data, salvo em arquivo JSON local) é razoável para uma contagem aproximada, mas note que
em ambiente serverless (Vercel) o sistema de arquivos é efêmero/read-only por instância — o
comentário no próprio código já reconhece isso ("Em produção serverless sem disco gravável, mantém
em memória durante o ciclo") — ou seja, a contagem provavelmente reinicia a cada cold start em
produção, tornando o número menos confiável do que a UI sugere.

7.3 [BAIXA] Badge fixo "Vercel Web Analytics: Ativo em Tempo Real" (Navbar.tsx, linha ~266) é
exibido de forma incondicional, sem checar se o Vercel Analytics está de fato coletando dados

7.4 [BAIXA] Inconsistência de contrato de dados: `RawFundamentalData.financialDebtToEbitda` é
